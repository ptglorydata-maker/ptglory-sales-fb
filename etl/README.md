# Pipeline ข้อมูลรายเพจ (U4 ยืนยันแล้ว, กำลังขยายไปยูนิตอื่น)

## เป้าหมาย
ดึงข้อมูลยอดขายรายวัน **ต่อเพจ** ของแต่ละยูนิต ย้อนหลังตั้งแต่ ม.ค.69 ถึงปัจจุบัน
โดย join กับไฟล์ master catalog ("test-รายงานเพจ FB") เพื่อรู้ว่าเพจไหน active/ใครดูแลอยู่
แล้วเขียนผลลัพธ์แบบ normalize (long-format) ลง Staging Sheet ให้ dashboard
(https://ptglorydata-maker.github.io/ptglory-sales-fb/) อ่านต่อได้

## สิ่งที่ตรวจสอบแล้วจากไฟล์จริง (ยืนยันด้วย U4)

**Master catalog** — flat table `UNIT | เพจ | แอดมิน | ชื่อไฟล์ | link`
1 แถว = 1 คู่ (เพจ × แอดมิน) เพจเดียวอาจมีแอดมินหลายคน คอลัมน์ `ชื่อไฟล์`/`link` มีค่าแค่บาง
แถวเท่านั้น (ไม่ครบทุกยูนิต) — ต้องขอลิงก์ไฟล์ต้นทางของแต่ละยูนิตเพิ่มเองตอนขยาย

**ไฟล์ต้นทางระดับยูนิต** (เช่น U4 HaYeon 69) — ซับซ้อน ยืนยันจริงจาก `--discover` แล้วว่า:
- มี tab สรุปยอดขายรายเดือนของทั้งยูนิต (ไม่แยกเพจ) และ tab "สรุปยอดเมื่อวาน_เพจ" ที่เป็นแค่
  สแนปช็อตวันล่าสุดวันเดียว ไม่ใช่ประวัติย้อนหลัง
- ข้อมูลรายวันย้อนหลังจริงอยู่ใน **1 tab ต่อ 1 เพจ** (U4 มี 6 tab ตรงกับ 6 เพจที่มีจริง)
- ภายใน 1 tab เพจ ข้อมูลหลายเดือนวางซ้อนกันในแนวตั้ง แต่ละเดือนมีบล็อกหัวตารางของตัวเอง
  (merged cells, มีคำว่า "วันที่" ซ้ำทุกบล็อก) ตามด้วยแถวข้อมูลรายวัน (เช่น `01/01/26`)
  จนกว่าจะเจอหัวตารางบล็อกเดือนถัดไป

**ชื่อ tab กับชื่อเพจใน master catalog สะกดไม่ตรงกัน 100%** (catalog มี `[P1] ` นำหน้า,
บาง tab มี `เพจ` นำหน้า, บางอันเว้นวรรค/ขีดไม่เหมือนกัน) — ทดสอบแล้วว่า exact match ล้มเหลว
ทุก tab ต้องจับคู่ด้วยมือผ่าน `tab_to_catalog` ต่อยูนิตแทน (fuzzy match เสี่ยงจับคู่ผิดเพจ)

**ผังคอลัมน์ไม่คงที่แม้แต่ภายใน tab เดียวกัน** — เจอบั๊กจริงตอนทดสอบ U5: ตอนแรก hardcode
เลขคอลัมน์ (col2/5/54/60) ไว้ตายตัวจากการเช็คบล็อกเดือนแรก แล้วสมมติว่าทุกบล็อกเดือนในเพจ
เดียวกันใช้ตำแหน่งเดียวกัน — ผิด เพราะถ้าเพจไหนมีแอดมินเพิ่ม/ลดระหว่างปี ส่วนหัวตารางของบล็อก
เดือนนั้นจะกว้าง/แคบกว่าเดือนอื่น ทำให้ค่าแอด/ROAS เลื่อนไปคนละคอลัมน์กันในแต่ละเดือน (เจอ
`sales` เป็น 0 ตลอดทั้งที่ `ad_spend`/`roas` มีค่า — เพราะคอลัมน์เลื่อนไปอ่านผิดที่)

**แก้แล้ว (รอบ 1):** ค้นหาตำแหน่งคอลัมน์จากข้อความหัวตาราง ("ยอดขาย" ตัวแรก, "Order"
ภาษาอังกฤษ, "ค่าแอด", "ROAS\nรวม") **ใหม่ทุกบล็อกเดือน** (`find_metric_columns`) แทน
เลขคอลัมน์คงที่ ไม่ต้องมี column mapping ในไฟล์ config อีกต่อไป

**เจอเคสที่ 2 หลังแก้รอบแรก:** U5 บางเพจ (เช่น DWAWA-Ginseng บาลานซ์พลัส) ตั้งแต่เดือน
7/2569 เป็นต้นไป ทีมเปลี่ยนป้ายกำกับยอดขาย/ออเดอร์รวมจาก "ยอดขาย"/"Order" เป็น "ยอดรวม"/
"Order รวม" พร้อมย้ายไปคอลัมน์ไกลออกไปมาก (มีตารางสรุปใหม่แทรกเพิ่มตรงกลาง) แต่ค่าแอด/ROAS
รวมยังอยู่ตำแหน่งเดิม ยืนยันด้วยการเปิดไฟล์จริงเทียบ ROAS×ค่าแอด ≈ ยอดขายจริงที่คอลัมน์ใหม่
(ตัวอย่าง 01/07/69: ค่าแอด 5,846 × ROAS 2.42 ≈ 14,147 ใกล้เคียงยอดขายจริง 14,120)
`find_metric_columns` จึงลองหาป้าย "ยอดรวม"/"Order รวม" ก่อน แล้วค่อย fallback ไปป้าย
"ยอดขาย"/"Order" แบบเดิมถ้าไม่เจอ (บล็อกแบบเก่าไม่มีคำว่า "ยอดรวม" เลย จึงไม่ชนกัน)

## คอลัมน์ที่ดึง (อัปเดต 8/8/2569)

ขยายจากเดิม (ยอดขายรวม/ออเดอร์รวม/ค่าแอด/ROAS รวม) เป็นชุดเต็มตามที่ขอ — mapping ต่อป้าย
หัวตารางจริงที่ยืนยันแล้ว (ดูรายละเอียดใน `find_metric_columns`):

| Staging column | ป้ายหัวตารางในไฟล์ต้นทาง | หาจากแถวไหน |
|---|---|---|
| `ad_spend` | "ค่าแอด" | label_row |
| `chats_ads` | "สนทนารายใหม่" | label_row |
| `chats_admin` | "รวมคนเข้าจริง" | group_row |
| `cost_per_chat` | "ต้นทุน\nต่อทัก" | label_row |
| `sales_total` | "ยอดรวม" (ก.ค.69+) หรือ "ยอดขาย" (เก่า) | label_row |
| `sales_new` | "ยอดรวมใหม่" หรือ 2 คอลัมน์แรกของกลุ่ม "ลูกค้าใหม่(เพจ)" | label_row / group_row |
| `sales_old` | 2 คอลัมน์แรกของกลุ่ม "ลูกค้าเก่า..." หรือคำนวณ (รวม − ใหม่) | group_row / derived |
| `orders_total` | "Order รวม" (ก.ค.69+) หรือ "Order" (เก่า) | label_row |
| `orders_new` | "Order ใหม่" หรือคอลัมน์ที่ 2 ของกลุ่ม "ลูกค้าใหม่(เพจ)" | label_row / group_row |
| `orders_old` | คอลัมน์ที่ 2 ของกลุ่ม "ลูกค้าเก่า..." หรือคำนวณ (รวม − ใหม่) | group_row / derived |
| `close_rate_new` | "%ปิดใหม่" | banner_row |

| `roas_new` | "ROAS\nใหม่" | banner_row |

| `error_pct` | "% Error" | banner_row |

**`sales_old`/`orders_old` ไม่มีคอลัมน์ตรงๆ ที่ระดับเพจในบล็อกแบบใหม่ (ก.ค.69 เป็นต้นไป)**
มีแต่ระดับรายแอดมิน สคริปต์จึงคำนวณจาก `รวม − ใหม่` แทนเมื่อหาคอลัมน์ตรงๆ ไม่เจอ — ถือว่า
สมเหตุสมผล (ยอดขายทั้งหมด = ใหม่ + เก่า) แต่ควรสุ่มเช็คกับตัวเลขจริงเป็นระยะ

## ทำไมต้องมี --discover ก่อนเสมอ

`sync_pages.py --discover <UNIT>` จะต่อ Google Sheets API จริงแล้วพิมพ์รายชื่อ tab ทั้งหมด
`sync_pages.py --discover <UNIT> "ชื่อ tab"` พิมพ์ตำแหน่งบล็อกรายเดือน (auto-detect จากคำว่า
"วันที่") พร้อมคอลัมน์ที่หาเจอในแต่ละบล็อก (sales/orders/ad_spend/roas) — ใช้ตรวจสอบก่อนว่า
เพจนี้มีโครงสร้างหัวตารางแบบที่สคริปต์รู้จักไหม (ถ้าหาคอลัมน์ไม่ครบจะขึ้น `None` ให้เห็นทันที)

การอ่านไฟล์ผ่านตัวแปลง Markdown (ไม่มี service account) ไม่สามารถให้ตำแหน่ง/ข้อความหัวตาราง
ที่แม่นยำได้ (merged cell ถูกแปลงเป็นข้อความซ้ำ) ต้องยืนยันด้วย gspread ของจริงก่อนเพิ่มยูนิต

## ขั้นตอนติดตั้ง (ทำครั้งเดียว)
1. `pip install -r requirements.txt`
2. ขอไฟล์ credentials (JSON key) ของ `glory-sheets-reader-456@ptglory-dashboard-sales-fb.iam.gserviceaccount.com`
   ตั้ง env var: `export GOOGLE_SERVICE_ACCOUNT_JSON=/path/to/key.json`
3. สร้าง Google Sheet เปล่าไว้เป็น Staging แล้วแชร์สิทธิ์ "Editor" ให้ service account ด้านบน
   (ทำแล้ว — ID อยู่ใน `STAGING_SHEET_ID` ของ `sync_pages.py`)

## ขั้นตอนเพิ่มยูนิตใหม่ (ทำซ้ำต่อยูนิต)
1. แชร์สิทธิ์ "Viewer" ให้ service account กับไฟล์ต้นทางของยูนิตนั้น
2. เพิ่ม entry เปล่าใน `UNITS` ของ `sync_pages.py` พร้อม `source_sheet_id` ของยูนิตนั้น
3. รัน `python sync_pages.py --discover <UNIT>` ดูรายชื่อ tab ทั้งหมด (คาดว่าจะเป็น 1 tab/เพจ
   เหมือน U4 แต่ต้องยืนยันจริง ไม่ใช่ทุกยูนิตจะมีโครงสร้างเหมือนกัน — บาง tab ในไฟล์เป็น tab
   สรุป/tab ต่อแอดมิน ไม่ใช่ tab ต่อเพจ ต้องดูชื่อ tab ให้ดีก่อนเลือก)
4. รัน `python sync_pages.py --discover <UNIT> "ชื่อ tab"` ทีละ tab ที่เป็นเพจ active ตาม
   master catalog เพื่อดูว่าหาคอลัมน์ sales/orders/ad_spend/roas เจอครบทุกบล็อกเดือนไหม
   (ถ้าบล็อกไหนขึ้น `None` แปลว่าโครงสร้างหัวตารางต่างจากที่สคริปต์รู้จัก ต้องดูเพิ่ม)
5. เพิ่มชื่อ tab เข้า `page_tabs` และจับคู่ `tab_to_catalog` สำหรับเพจที่ active
6. รัน `python sync_pages.py --unit <UNIT>` เพื่อ sync ยูนิตนั้นลง Staging Sheet
   (ไม่กระทบข้อมูลยูนิตอื่นที่ sync ไว้ก่อนแล้ว)
7. เปิด Staging Sheet เช็คว่า `active`/`admin` ถูกต้อง และยอดขายสมเหตุสมผลทุกเดือน (ไม่ใช่แค่
   เดือนแรก) — เทียบกับตาราง "สรุปปี69" ของยูนิตนั้น

รัน `python sync_pages.py --all` เพื่อ sync ทุกยูนิตที่มี config ครบแล้วในครั้งเดียว

## ระวัง: ทีมอาจเปลี่ยนชื่อ tab ในไฟล์ต้นทางได้ตลอดเวลา

เจอจริงกับ U4 (8/8/2569): มีคนเปลี่ยนชื่อ tab จาก `"Ha Yeon - ครีมโสมลดฝ้า"` เป็น
`"P3 Ha Yeon - ครีมโสมลดฝ้า"` ทำให้ `python sync_pages.py --unit/--all` พังด้วย
`gspread.exceptions.WorksheetNotFound` ถ้าเจอ error นี้ ให้รัน `--discover <UNIT>` ใหม่
เพื่อดูชื่อ tab ปัจจุบัน แล้วแก้ `page_tabs`/`tab_to_catalog` ของยูนิตนั้นให้ตรง — ไม่ใช่บั๊ก
ของสคริปต์ แค่ไฟล์ต้นทางเปลี่ยนโดยไม่แจ้งล่วงหน้า

## ขั้นต่อไป
- เพิ่ม mode ใหม่ในฝั่ง Cloudflare Worker (เช่น `mode=pages&unit=U4`) อ่านจาก Staging Sheet
- เพิ่ม section "รายเพจ" ในหน้า dashboard (`index.html`) แสดงเพจ active/inactive ต่อยูนิต
  พร้อมกราฟยอดขายรายวัน/เดือนต่อเพจ
- ถ้าข้อมูลโตจนช้า (หลายยูนิต × รายวัน × หลายปี) ค่อยย้าย Staging จาก Google Sheet ไป BigQuery
